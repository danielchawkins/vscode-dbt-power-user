## Reading the tables

- Step: the directory under `$TMPDIR/fpu-ev/cli-read/` holding `command.txt`, `stdout.txt`, `stderr.txt`, `files-after.txt` and `result.json`.
- Argv: `result.json` `argv`, with the project directory shown as `<P>`, the binary as `<dbt>`, and the run directory as `<OUT>`. Arguments that contain spaces or quotes are JSON-quoted, and `\n` is a newline inside an argument. In `r8`, `"$PQ_SCRIPT"` stands for the Python program written out in `experiments/r8-parquet-compare.sh`.
- Extra env: variables beyond the base environment (`HOME`, `PATH`, `TERM=dumb`, `DBT_PROFILES_DIR=<P>`, `DBT_ENGINE_PROFILES_DIR=<P>`, `DBT_SEND_ANONYMOUS_USAGE_STATS=false`). `SO` means only `FUSION_POWER_USER_SCHEMA_ORIGIN=local`, `+ X` means `SO` plus `X`, and `none` means nothing extra.
- ms: `ended - started` from `result.json`. Both timestamps are taken by separate `node` processes around the command, so they include the harness floor measured in `r5` (32–41 ms for `/usr/bin/true`).
- Output: the row count when stdout parses as a JSON array, then the stdout size and the first 90 characters with `\n` and `\t` escaped. A space at the very start or end of an excerpt is shown as `␣`. For a non-zero exit it shows the first `[error]` line of stderr. For `--output table --limit 0` it shows the header's columns and the last line. For `r8` pyarrow steps it shows the summary lines the script prints.

## What the recorded runs show

In this fixture with this binary:

1. **Only `--quiet` with a data format gives a clean stdout.** With `--quiet`, stdout is exactly the payload and stderr is empty, for `table`, `csv`, `tsv`, `json`, `ndjson` and `yml` (r1 steps 03–06, 11–14, 19–22, 27–30, 35–38, 43–46). Without `--quiet`, stdout starts with seven spaces and `dbt 2.0.6` on the first line, and ends with a blank line, the `Execution Summary` banner and `Finished 'show' successfully [NNms]`. So `JSON.parse(stdout)` fails (r1 31–34; r2 04, 06).
2. **Each format has its own framing.** `json` is one line, `[…]\n` (r1 28). `ndjson` is one object per line followed by an empty line (r1 35, 37). `csv` and `tsv` are a header line, the rows, and an empty line (r1 11–14, 19–22). `yml` is `---`-separated documents with keys sorted alphabetically (r1 43). `table` starts with a `Query info_schema_column_lineage` line, then a box-drawn table, then a row-count line (r1 03–06). `--inline` tables start with `Query info_schema_inline` instead (r3 32).
3. **`--output selector`, `name` and `path` are rejected.** Each exits 1 with `[error] [UnsupportedFeature (dbt0255)]: DisplayFormat::<X> is not supported for tabular data display` on stderr. With `--quiet`, stdout is empty (r1 51–74).
4. **`--limit` means different things per format.** The default returns 10 rows (r1 27; r3 31). `--limit -1` returns all 32. `--limit 5` returns 5. `--limit 0` returns all 32 for `json`, `ndjson`, `csv`, `tsv` and `yml` (r1 13, 21, 29, 37, 45), but zero rows for `table`, with the footer `32 rows, showing only 0 rows. Run with --limit -1 to show all rows.` (r1 05). The table footer at the default limit reads `10 rows, showing only 10 rows.`, not 32 (r1 03).
5. **`--log-format json` and `otel` put log events on stdout even with `--quiet`.** Under `json` and `otel`, stdout is NDJSON log events (5 and 6 lines), and the rows appear only as a JSON string inside one event. For `json` that is `ShowNode`/`Q041` `data.preview`; for `otel` it is `ShowDataOutput` `attributes.content` (r2 07–12). `default` and `text` behave identically (r2 03–06).
6. **`--inline` over `info_schema()` accepted every DuckDB feature tried.** That covers `WHERE` equality, `IN`, tuple `IN`, `GROUP BY`, `DISTINCT`, `LEFT JOIN` to `node_columns`, `JOIN` to `models`, `NOT EXISTS`, `WITH RECURSIVE` with `UNION` and `UNION ALL`, `USING KEY`, window functions, `QUALIFY`, `ILIKE`, `list(struct_pack(...))`, `string_agg`, Jinja `{% set %}`, and `read_parquet('target/info_schema/v1/…')` (r3 03–14, 16–24, 28, 29). The recursive queries walked `totals_downstream.grand_total` up to `raw.orders.amount` and `raw.orders.customer_id` at depth 3, and walked `raw.orders.amount` down to four columns (r3 16–19).
7. **`--inline` failures are SQL-level errors on stderr.** Writing `dbt.column_lineage` directly fails with `Generic (dbt1000)` `Catalog Error … schema "dbt" does not exist` (r3 15). SQL errors come back as `InvalidArgument (dbt1007)` with DuckDB's `Binder Error` or `Parser Error` text, which shows that `info_schema('column_lineage')` rendered as `dbt.column_lineage` (r3 25, 26). Two statements return the second statement's result (r3 30). Nested values come back as flattened keys (`parents.0/p`, `tags.0`) (r3 21, 14).
8. **`dbt show` exposes 37 views; 12 have rows here.** Those are `project` 1, `packages` 1, `project_env_vars` 1, `models` 4, `sources` 3, `macros` 524, `docs_blocks` 1, `dag_nodes` 7, `edges` 627, `node_columns` 25, `column_lineage` 32 and `invocations` 1 (r4 04–77). `run_results_latest`, `resources` and `node_input_files` are defined in `views.sql` but `info_schema()` rejects them with `dbt1007 … is not available to dbt show` (r4 78–80). `invocations`, `run_results`, `diagnostics` and `adapter_queries` have no `ingested_at` column (r4 67, 69, 75, 77).
9. **A read costs about 75–90 ms wall clock.** That includes a 32–41 ms harness floor. `show --info` took 74–81 ms, the inline WHERE 77–79 ms and the inline recursive query 81–89 ms (r5 03–15). Across 5 repeats there was no warm-up trend.
10. **`show --info` and `--inline` over `info_schema()` never touched `probe.duckdb`.** Its sha256 was identical before and after (r6 05, 09, 19). Both reads succeeded with the file moved away and did not recreate it (r6 11–14). They changed only `logs/` (r6 `files-after.txt` 05→06, 10→11, 12→13). Their 51 query-log entries are `CREATE SCHEMA`/`CREATE VIEW` over `read_parquet` of `target/private/metadata/…` plus the final `select`, and none refers to the warehouse (r6 07). In contrast, `--inline "select 1 as x"` with no `info_schema()` created a new 12288 B `probe.duckdb`, logged a `dbt run query`, and rewrote `target/manifest.json` and `target/run_results.json` (r6 15–17). `show -s stg_orders` queried `"probe"."main"."orders"` (r6 21).
11. **`show --info` reads `target/private/metadata/`, not `target/info_schema/`.** With `target/info_schema/` deleted, or with its `dbt.column_lineage.parquet` deleted, it still returned 32 rows (r7 18, 21). The query log reads only `target/private/metadata/` (r6 07).
12. **Missing or stale metadata fails in two ways.** With no `target/private/metadata`, meaning before any compile, after `dbt clean`, or with `--target-path target-other` / `DBT_TARGET_PATH=target-other`, the command exits 1 in about 40 ms with `InfoSchemaUnavailable (dbt1656): no project metadata at <P>/<target>/private/metadata — …` on stderr (r7 02–04, 13, 16, 26). Without `--quiet`, stdout also carries the banner and `Finished 'show' with 1 error` (r7 04). A compile without `--generate-info-schema` (r7 06), or with `--static-analysis baseline` (r7 09), gives exit 0 and `[]`. There is no error to tell that apart from "no lineage". The baseline compile warns on stderr `--generate-info-schema: column types will not be populated without --static-analysis strict …` (r7 08). An absolute `--target-path <P>/target` works (r7 15).
13. **Does reading the parquet ourselves give anything `dbt show --info` does not?** For column lineage, no new rows and no new lineage columns. All three lineage parquet files (`target/info_schema/v1/`, `target/private/metadata/compile/`, `target/private/index/`) hold the same 32-row multiset as the show JSON on every column (r8 08, 09, 17). What the parquet adds is representation only:
    - `ingested_at` as a `timestamp[us, tz=UTC]`, where show gives a local-offset string for the same instant;
    - nullability flags;
    - the key-value metadata `dbt:info-schema-version=1` (info-schema files only);
    - for `node_columns`, `tags` and `classifiers` as real lists, where show gives flattened `tags.0` and `classifiers.0` (r8 11).

    The private files use other column names and `int32` or `not-null` types (r8 09, 11). `target/private/index/` was absent after a plain compile and present after `compile --write-index` (r8 10, 13), and it holds files with no `dbt show` view, such as `column_stats`, `sample_data` and `catalog_*` (r8 13). This run did not read their contents.

- Whether the `InfoSchemaUnavailable` message or the `ShowNode`/`ShowDataOutput` event shapes are stable across Fusion versions.

- Why `--limit 0` differs between `table` and the other formats, and whether the table footer's total at the default limit is a count or the shown size. Both runs show only the observed output.
