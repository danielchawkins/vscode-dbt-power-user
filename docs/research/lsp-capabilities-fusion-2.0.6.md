# dbt Fusion 2.0.6 language server capabilities

Captured 2026-10-03 against `dbt lsp` 2.0.6 (`/Users/daniel/.local/share/mise/installs/aqua-getdbt-com-dbt-fusion/2.0.6/dbt`, `serverInfo` `dbt-lsp 2.0.6`), Darwin arm64, over stdio with `vscode-jsonrpc`. The harness is `scripts/spikes/lsp-capabilities/`; raw request and response JSON is under [`evidence/lsp-2.0.6/`](evidence/lsp-2.0.6/). Latencies are the p50 of five requests unless a row says otherwise.

Two projects:

- **jaffle**: `test-fixtures/jaffle-shop-duckdb` copied to `/tmp`, extended by `prep-jaffle.sh` with a macro, a dotted `jaffle_shop.cents_to_dollars` call, a source, an exposure and a singular test, then `dbt build` (7 models, 3 seeds, 21 data tests, 1 unit test, 1 source, 1 exposure). Server argv: `lsp --project-dir <P> --profiles-dir <P> --lint-enabled false --no-version-check --command-prefix "" --static-analysis strict`, env `DBT_LSP_USE_TARGET_LSP=1`.
- **finance**: a copy of `finance_general` without `target/` and `logs/` (330 models, 1,270 sources, 831 macros, Snowflake), so the server never wrote into the original. Run from the `fpu-settings` mise environment with `--profiles-dir ~/.dbt`. Snowflake key-pair auth worked. Runs with `--static-analysis baseline` and `strict`. Row values from Snowflake are replaced with their JSON type in the committed evidence.

Each section ends with what the runs show. Files: `jaffle/`, `finance-strict/`, `finance-baseline/` hold `initialize.json`, `summary.json` (one row per probe: params, ok, p50, samples, shape), `requests.json` (first response of each probe), `listNodes.json`, `freshness.json`, `diagnostics.json`, `notifications.json`, `load.json`; `bench/` holds the LSP-versus-CLI timings, the code lens matrix, the column-lineage matrix, the config-error runs and follow-up checks.

There is no `experimental` field and no custom capability. After `initialized` the server sends one `client/registerCapability` for `workspace/didChangeWatchedFiles` with `globPattern: "**/*"`, and asks `workspace/configuration` for section `dbt` before every compile. `strings` on the binary shows that section is read into a `RawLspSection` with fields `maxErrorReporting`, `linter` and a formatter config; the probe answered `{lsp:{linter:{enabled:false}}}` as the extension does. No `initializationOptions` field was found; the earlier capture showed four variants left the result unchanged.

## Load

- The server does nothing until the first `textDocument/didOpen` (as on 2.0.5). Then: an incremental compile of that file, `dbt/lspCompileComplete`, then a background full compile and `dbt/lspBackgroundCompileComplete`.
- jaffle: `didOpen` → `dbt/lspCompileComplete` 193 ms, → background complete 1.5 s. finance baseline: 3.8 s and 8.2 s; finance strict: 4.4 s and 18.2 s (strict fetches every upstream schema from Snowflake once).
- Every `dbt/*` compile notification carries `cause: "didSave"` whatever triggered it. Params: `adapter_type`, `adapter_unique_id`, `cause`, `compile_type` (`incremental` or `full`), `dbt_version`, `duration_ms`, `errors[]` (`{code, message, severity}`), `models_count`, `project_id`.
- The server also sends `workspace/codeLens/refresh` and `workspace/semanticTokens/refresh` after every compile, and two notifications not seen in earlier captures: `dbt/renameModel` and `dbt/renameColumn`, both with params `{}`, during rename probes.
- `dbt.getProjectInfo` returns `{}` until the first compile completes, then `{"adapter_type","models_count","models_count_is_estimate":false,"project_name"}`.

## `dbt.listNodes`

Arguments are selector strings, one per array element; several elements are a union (`["orders", "customers"]` → 4 nodes). An object argument is rejected (`empty selector list passed to --select/--exclude`); a trailing object is ignored (`["+orders+", {depth: 1}]` = `["+orders+"]`). There is no depth parameter: depth is the selector's `n+` prefix and `+n` suffix.

A project-grain node is `{unique_id, name, resource_type, package_name, original_file_path, depends_on:{nodes:[…]}, config:{materialized, access, group}}`. There is no description, column list, tags, meta, database/schema/alias, raw or compiled SQL, test metadata, patch path, or child list; children and counts have to be inverted from `depends_on` across the returned set. One `package:<root>` call returns the whole project graph in 23 ms (J) and 64 ms (F, 1,600 nodes), so `childCount`/`parentCount` can be computed client-side from one request.

Two concurrent `dbt.listNodes` requests: the earlier one returns `{"error":"Operation cancelled"}` in 12 ms; the later one answers. `dbt.show`, `dbt.getCurrentNode` and `dbt.compileFile` sent together with each other all answered.

## Column lineage

`["@<uid>", "+column:<uid>.<COLUMN>+"]` is the only form that returned nodes (the official extension's form). `+column:…+` alone, `column:…+`, `+column:…` and `1+column:…+1` returned `grain: "column", nodes: []` on every model in both projects, even where the `@` form returned nodes. A column node is `{unique_id: "<node uid>.<COLUMN>", name, node_name, resource_type, materialized, original_file_path, op: "copy"|"mod"|"unknown", transformation_type: "transformation"|"raw"|…, is_primary_key, parents: ["<uid>.<COL>"]}`.

- The column must be spelled as `dbt.getCurrentNode` reports it. On Snowflake that is upper case; the lower-case spelling returned 0 nodes.
- jaffle: every model answered (`orders.amount` → `stg_payments.amount` → `raw_payments.amount`, 3 nodes, 37 ms). The depth prefix had no effect (`2+column:` gave the same 3 nodes).
- finance strict ([`bench/finance-column-lineage.json`](evidence/lsp-2.0.6/bench/finance-column-lineage.json)): base models built from a source answered (`base__stripe_grant__topup.AMOUNT` → the source column, 2 nodes); the three staging models built by `kikoff.union_relations` or `temporalize.reconcile` answered 0 nodes for every column, although `dbt.getCurrentNode` returned their typed columns. Each request took 600–700 ms in F (37 ms in J).
- Baseline returns 0 nodes everywhere.

## `dbt.show`

- `{uri}` runs the model's compiled SQL; in J it returned all 99 rows of `orders`, so no default limit was observed. `{uri, limit}` applies a limit; `{inline, limit}` runs Jinja-SQL against the project; `{uri, inline, limit}` runs `inline`. `limit: -1` returns `null`; `limit: 0` returns columns and no rows.
- Result: `{columns: [name…], data: [{name: value}…], error: null}`. Values are JSON strings for numbers, booleans for booleans, ISO strings for dates, `null` for nulls ([`jaffle/show-typed.json`](evidence/lsp-2.0.6/jaffle/show-typed.json)). There are no column types; a typed header needs `dbt.getCurrentNode` (for a model) or Jinja introspection: `{{ adapter.get_columns_in_relation(source('raw','raw_orders')) }}` inside `inline` returned names and dtypes in 35 ms ([`bench/extras.json`](evidence/lsp-2.0.6/bench/extras.json)).
- No compiled SQL is returned with the result. A SQL error is `{columns:null, data:null, error:"Internal: Parser Error: …"}` (DuckDB) or `"Internal: [Snowflake] 001003 (42000): SQL compilation error: …"`; an unknown `ref` fails at render in about 30 ms.

## CTE preview

Fusion's code lens argument gives the compiled file and the byte range `[compiled_start, compiled_stop)` from `with` to the end of that CTE's body, without the closing parenthesis. `dbt.show` with `inline` = that slice + `"\n)\nselect * from <name>"` returned the CTE's columns and rows (J 35 ms, F 2.5 s). Lenses are returned only while the document is unchanged since its last save. They do not depend on the static-analysis mode or on the language id (`jinja-sql` or `sql`) ([`bench/jaffle-lenses.json`](evidence/lsp-2.0.6/bench/jaffle-lenses.json)).

## Freshness and file watching

[`jaffle/freshness.json`](evidence/lsp-2.0.6/jaffle/freshness.json), [`finance-strict/freshness.json`](evidence/lsp-2.0.6/finance-strict/freshness.json):

- **The server watches the disk itself.** A model with no open document, edited on disk with no notification, was recompiled by a background full compile within 8 s (no `dbt/lspCompileComplete`, but `getCurrentNode` showed the new column) in J and in F strict. In F baseline the same edit was not reflected; that run's model has no columns in baseline, so the check could not see it.
- `workspace/didChangeWatchedFiles` (Changed) on that file recompiled it in 15–64 ms. Created: a new model became listable after one compile (183 ms J, 1.4 s F).
- An unsaved `didChange` triggers no compile and is not reflected by `getCurrentNode`, `compileFile`, code lenses or semantic tokens; lenses and tokens return `null` until the next save.
- `didSave` of changed text recompiles (101 ms J, 1.3 s F) and is reflected by `getCurrentNode`, column lineage and `listNodes`.
- The server never writes `target/manifest.json`, `catalog.json` or `run_results.json`. Its output is `target/.lsp/{compiled,data,db,generic_tests,private,snapshots}` (`DBT_LSP_USE_TARGET_LSP=1`).

## Must stay in the extension

- **Documentation editor fields.** Descriptions, column descriptions, tests on a model (generic tests never appear in `listNodes`), `meta`, tags and doc blocks are not exposed by any command; hover shows column descriptions only as rendered Markdown. The docs editor keeps reading `manifest.json`, so a CLI `dbt parse` stays for it.
- **Macro inventory and doc blocks.** `resource_type:macro` and `resource_type:doc` return no nodes; no command lists macros.
- **Source YAML generation.** `generateSchemaYML` needs a relation's columns and types; `getCurrentNode` gives them only for models. It can move to `dbt.show` with Jinja introspection, but the YAML writing stays in the extension.
- **Run, build, test, compile tasks, `deps`, `docs generate`, `clean`, `debug`.** The server has no command to run, build, test, install packages or generate docs. These stay CLI tasks.
- **Configuration errors that stop the project loading** (unknown target, unset `env_var` in `profiles.yml`): the server sends no diagnostic, log line or notification. The extension's CLI check (`dbt parse` or `dbt debug`) and `projects/projectErrors.ts` stay.
- **Unsaved-text compile and preview.** `compileFile`, lenses and tokens reflect the last save. Previewing unsaved SQL means `dbt.show {inline}` with the editor text (works), not `compileFile`.
- **Highlighting.** Semantic tokens cover columns, Jinja variables, `ref` and some macro calls on clean documents only, and return `null` after any unsaved edit; the TextMate grammar stays.
- **Request serialisation.** Concurrent `dbt.listNodes` requests cancel each other; the client queue in `fusion/fusionLanguageClient.ts` stays.
- **Static-analysis detection.** Column hover, references, rename, types and column lineage need strict; the extension must keep reporting the mode (`dbtLineageService.whyEmpty`).

## `docs/lsp-metadata-gaps.md` is stale

Stale claims:

- "`dbt.listNodes` … returned `null`" and "depth cannot be sourced from the LSP": with a selector string it returns the node graph with `depends_on`, n-hop selectors and the whole project in one call. `modelDepthMap` and `GraphMetaMap` can be computed from it.
- "`dbt.getCurrentNode` returned `null`": with `[relpath]` it returns `unique_id`, database, schema and typed columns.
- "Sources (`SourceMetaMap`) … none advertised" and "Exposures … none advertised", "Unit tests … not captured", "Functions … not captured": `listNodes` returns source, exposure, unit test and function nodes with paths and dependencies.
- "`models_count` 0 and `models_count_is_estimate` true" as the characterisation of `getProjectInfo`: after load it is exact.

Still true: no command returns macro metadata (`MacroMetaMap`), doc blocks (`DocMetaMap`), generic test metadata (`TestMetaMap`), metrics or semantic models, or node descriptions, tags, meta, or raw and compiled SQL. The conclusion that no contract-complete LSP `ProjectMetadataSource` can be written still holds; the reason is these missing fields, not null results.
