# Fusion Power User: read-only practice review (main @ `nrzmvmru` / `f939c18a`, 2026-10-03)

**Verdict: land-with-fixes.** The framework migration is complete: no Inversify, Redux, react-router, Bootstrap, SCSS, Tailwind, Storybook, Altimate package, Python bridge or Core/Cloud runtime path is left. The biggest remaining gap is **dbt LSP coverage**. Several user-facing features still start a fresh `dbt` CLI process for work the running Fusion language server already answers: the compiled preview, query preview, CTE profiling, model columns and table lineage. The decision record that keeps them on the CLI (`docs/lsp-metadata-gaps.md`) relies on captures that the repository's own later evidence shows used the wrong argument shapes.

Scope: static reading, `rg`, `npx knip --no-progress` and `npx depcruise src --config .dependency-cruiser.cjs --output-type err`. I built nothing, installed nothing and modified nothing. Standard: `docs/research/vscode-extension-practice-september-2026.md` (cited below as "practice §N"), plus current samples and `vscode-languageclient` practice.

## 1. Ranked findings

### Must-fix (correctness, a stale decision record, or a recorded decision violated)

1. **`docs/lsp-metadata-gaps.md` is stale and blocks LSP adoption.** Its `NodeMetaMap/GraphMetaMap`, `modelDepthMap` and "Column metadata" rows (`lsp-metadata-gaps.md:21-23`) cite `dbt.listNodes` → `null` and `dbt.getCurrentNode` → `null`. The addendum in `docs/research/lsp-commands-fusion-2.0.5.md` ("Resolved 2026-09-23") and `docs/research/evidence/lsp-protocol.md` P3 show those nulls came from the wrong argument shapes:
   - `listNodes ["+order_totals+"]` returns project-grain nodes with `depends_on`.
   - `getCurrentNode [relpath]` returns typed columns.

   `docs/architecture.md:72` repeats the stale claim. The conclusion that no single LSP producer covers the whole event (macros, docs, exposures, metrics) may still hold. However, the evidence for graph, depth and columns is wrong, and every "keep the manifest/CLI" choice below rests on this file. **Fix:** re-capture with the shapes in `architecture.md:34`, and rewrite the table to say which needs the LSP *does* cover.

2. **The compiled SQL preview starts a full CLI compile on each refresh while the LSP already has the result.**
   - `src/features/compiledSql/sqlPreviewContentProvider.ts:42-46` debounces every keystroke in the source model by 500 ms.
   - Each refresh then runs `project.unsafeCompileQuery` (line 130) → `FusionCli.compileInline` → `dbt compile --inline <buffer>` (`src/core/cli/cliArgs.ts:95-100`). That is a new Fusion process that re-parses the whole project.
   - Each refresh also shows a **Notification**-location progress toast (line 101-104), so typing produces a stream of "Compiling dbt model..." toasts.

   Fusion advertises `dbt.compileFile [uriString]`, which returns `target/.lsp/compiled/.../<model>.sql` in milliseconds (`lsp-protocol.md` P3). `FUSION_LSP_COMMANDS.compileFile` (`src/fusion/fusionLanguageClient.ts:39`) is defined, but nothing calls it.

   **Fix:**
   - Serve saved models from `compileFile`, refreshing on `dbt/lspCompileComplete`.
   - Keep `compile --inline` only for dirty buffers and untitled SQL, triggered on demand rather than per keystroke.
   - Move the progress to `ProgressLocation.Window` or the language status item's `busy`.

3. **The `fusionPowerUser.query.template` setting is contributed but never read.** It is declared at `package.json:235` and typed at `src/settings/index.ts:31,57`, but no production code reads it (`rg 'query.template' src` shows only the settings schema). Users who set it get no effect. **Fix:** delete the setting, or wire it into `normalizeQueryLimit` in `src/projects/projectSql.ts`.

4. **`capabilities.hoverProvider: true` is not a VS Code manifest field** (`package.json:24`). It is an upstream leftover. Only `untrustedWorkspaces` and `virtualWorkspaces` are recognised, and hovers come from the LSP. Delete it.

5. **`virtualWorkspaces` is undeclared.** The extension spawns `dbt` on `file:` paths and reads `fs` directly (for example `sqlPreviewContentProvider.ts:121`, `fusionCli.ts:51`). Without `"virtualWorkspaces": false`, VS Code treats the extension as supported in virtual workspaces (vscode.dev, GitHub Repositories), where it can only fail. Add `"virtualWorkspaces": { "supported": false, "description": "…runs a local dbt executable." }` next to `untrustedWorkspaces` (practice §1 and the virtual-workspaces guide).

6. **dependency-cruiser fails, with 4 `no-circular` errors** (gated only by the known-violations baseline):
   - `projects/manifestTypes.ts ↔ projects/project.ts`
   - `dbtPowerUserExtension.ts ↔ features/codeLenses.ts` (`codeLenses.ts:2` imports the extension class only for `DBT_SQL_SELECTOR`, which breaks "nothing imports features" in spirit)
   - `dbt_client/event/runResultsEvent.ts ↔ projects/project.ts`
   - `dbt_client/event/projectConfigChangedEvent.ts ↔ projects/project.ts`

   Plan R1.3 asked for `no-circular` "now". **Fix:**
   - Move the selectors to `src/fusion/` or `core/`.
   - Make the event classes carry an interface instead of `Project`.
   - Empty `.dependency-cruiser-known-violations.json`.

### Should-fix (design, convention, user-visible leftovers)

7. **The CLI is used where `dbt.show` over the LSP is available.** Every one of these call sites spawns a separate `dbt show --inline` or `dbt compile --inline` process, and each process re-parses the project:
   - `executeSQL` (`src/projects/projectSql.ts:97`)
   - the CTE profiler (`src/features/cte/cteProfilerService.ts:134`, one process per CTE)
   - `getColumnValues` (`projectSql.ts:227`)
   - `getColumnsOfModel` and `getColumnsOfSource` (`src/fusion/fusionCli.ts:342-361`)

   P3 shows `dbt.show [{inline, limit}]` and `[{uri, inline, limit}]` return `{columns, data}` from the live server.

   **Fix:** route preview, CTE profiling and distinct values through `client.request(FUSION_LSP_COMMANDS.show, …)` with CLI fallback when the client is not running. First, run one evidence experiment in `scripts/evidence/experiments/` covering three questions:
   - Does `show` cancel or serialize against a running compile? `dbt.listNodes` needed a queue: `fusionLanguageClient.ts:469-477`.
   - How does the server report errors?
   - What is the latency on a real project?

   For model columns, prefer `getCurrentNode` (static types, no warehouse), as the lineage panel already does (`lineagePanel.ts:621`). The docs editor still queries the warehouse (`docsEditPanel.ts:652,745`).

8. **Table lineage and the Parent/Children trees come from the manifest; column lineage comes from the LSP.**
   - `DbtLineageService.getConnectedTables` (`src/features/lineage/dbtLineageService.ts:211-241`) and the model trees read `graphMetaMap`. That map is rebuilt only after a CLI `dbt parse`, which `ManifestTrigger` runs 500 ms after any `.sql/.yml/.yaml/.csv` change (`src/projects/manifest.ts:313-371`).
   - Column lineage is read live from `dbt.listNodes` (`dbtLineageService.ts:112`).

   So one panel mixes two sources with different freshness. On every save, Fusion also parses the project twice: once in the LSP's incremental compile and once in the CLI `dbt parse`. The official extension gets project lineage from `listNodes ["+<unique_id>+"]` (evidence README §10). **Fix:** the decision needs an ADR, because it contradicts the "one producer" rule in `lsp-metadata-gaps.md`. One option is to take graph edges and depth from `listNodes` and keep the manifest for docs, tests, macros and semantic metadata. At minimum, re-measure the cost of the duplicate parse on a finance-pipelines project.

9. **The CTE code lenses come from an 815-line regex parser while Fusion emits CTE lenses.** `withoutUnregisteredLspLenses` (`fusionLanguageClient.ts:180-188`) drops Fusion's `dbt.previewCte` lenses, and `CteCodeLensProvider` (`src/features/cte/cteCodeLensProvider.ts`, 815 lines) re-detects CTEs with regular expressions. `docs/architecture.md:24` says "Extension code lenses remain because Fusion returns none", which contradicts the code comment. **Fix:**
   - Capture the `dbt.previewCte` lens arguments.
   - If they carry the CTE name and range, remap them in `middleware.provideCodeLenses` to `fusionPowerUser.runCteWithDependencies` and delete the regex detector.
   - Otherwise, correct the architecture sentence.

10. **Upstream vendor references are still in the shipped webview.**
    - Help links point to `https://docs.myaltimate.com/...` in four files: `webview_panels/src/modules/queryPanel/constants.ts:4-16`, `documentationEditor/components/help/TestsHelpContent.tsx:30`, `DocumentationHelpContent.tsx:55` and `lineage/components/help/HelpContent.tsx:35`. That sends users to another product's hosted docs (ADR 0001 product boundary).
    - `assets/icons/index.tsx:70` has alt text "Altimate loader".
    - Names and classes still carry the prefix: `AltimateSelect` and `.altimate-select` (`uiCore/components/select/index.tsx:118-158`, `select.module.css`), `altimatePerspectiveViewer` and `altimate-styles` (`PerspectiveViewer.tsx:162,301`).
    - The R3.5 exit grep covered only `src/`.

    **Fix:** link to docs.getdbt.com or remove the links, and rename to `Select`, `perspectiveViewer` and similar.

11. **Dead code and vestigial API surface.** knip reports 27 unused exports and 32 unused exported types. The plan says to run `just lint-unused` at the end of each phase and before each release. Notable entries:
    - `src/modules.ts` and its `@extension` alias, wired in `rsbuild.config.ts`, `vitest.config.ts` and `tsconfig.json`: all 5 exports are unused.
    - `DataPilotHealtCheckParams` and `HealthcheckArgs` (`src/dbt_integration/domain.ts:120,175`): Altimate DataPilot leftovers.
    - `FUSION_LSP_PREVIEW_CTE`, `FUSION_COMPILE_COMPLETE`, `CONNECTION_TIMEOUT_MS` and the backoff constants (`fusionLanguageClient.ts`) are exported only for tests.
    - `compileNode` CLI kind (`cliArgs.ts:14,93`): only tests use it.
    - `hashProjectRoot`, `resolveDefer`, `resolveFolderPath` and `resolveLspCompiledOutput`.
    - The `sendTelemetry` parameters on `DBTTerminal.info/warn/error` (`src/dbt_integration/terminal.ts:9,15,22`) are ignored (`outputChannels.ts:194-213`). That is a telemetry-shaped API in a no-telemetry product.
    - The stale comments `// in dbt cloud, packages are not downloaded locally` (`core/manifest/types.ts:23,75,147,181,215`) and `// Update Redux state` (`DocGeneratorInput.tsx:107`).
    - `scripts/spikes/lineage-renderer/` imports `@altimateai/ui-components`, `tailwindcss` and `bootstrap` from webview `node_modules`, none of which is installed any more, so the spike cannot run.

12. **The `Ctrl+'` / `Cmd+'` keybinding has no `when` clause** (`package.json:595`). It takes the key in every editor, Markdown and JSON included. Add `"when": "editorTextFocus && (resourceScheme == query-preview || resourceLangId == jinja-sql || resourceLangId == sql)"`.

13. **The `when` clauses show dbt menus on any SQL file.** `resourceLangId =~ /^sql$|^jinja-sql$/` appears about 15 times in `package.json:592-680`, so run/build/test icons appear on SQL files outside any Declared Project. The `jinja-sql` `filenamePatterns` (`**/models/**/*.sql`, `package.json:830-837`) also apply in non-dbt repositories. **Fix:**
    - Publish the project roots as a context key with `setContext('fusionPowerUser.projectRoots', [...])`.
    - Gate menus with `resourceDirname in …`, or with a `fusionPowerUser.inProject` key updated by `CurrentProject`.

14. **The `SqlActionsCodeLensProvider` lenses are noise.** It adds "Execute Query" and "Document" lenses at line 0 of *every* `.sql` (`src/features/sqlActions/sqlActionsCodeLensProvider.ts:24-40`). Both duplicate editor-title actions. Make them opt-in or remove them.

15. **The extension imports `vscode-languageserver-protocol` directly** (`package.json` dependencies; `fusionLanguageClient.ts:19`) only for `ExecuteCommandRequest`, which `vscode-languageclient/node` re-exports. The pins happen to agree (3.18.3 in both), but a languageclient bump could load two protocol copies. Import from `vscode-languageclient/node` and drop the dependency.

### 5.3 Paths that do the same thing twice

1. **Parse:** on every save, the LSP's incremental compile and the CLI `dbt parse` both parse the project (`manifest.ts:313` watcher → `fusionCli.ts:270`).
2. **Lineage:** manifest table edges (`dbtLineageService.ts:211`) plus LSP column edges (`dbtLineageService.ts:112`), in one panel, with different freshness.
3. **Compile:** the LSP already compiled the model into `target/.lsp/compiled/`, and the preview recompiles it with `dbt compile --inline` (`sqlPreviewContentProvider.ts:130`).
4. **Columns:** LSP `getCurrentNode` in the lineage panel versus a CLI warehouse query in the docs editor, for the same model's columns.
5. **Configuration errors:** CLI parse logs and LSP compile notifications. This one is deliberate, deduplicated in `ProjectErrors`, and acceptable.
6. **CTE detection:** Fusion lenses (dropped) and the regex detector.
