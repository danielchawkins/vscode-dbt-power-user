# Architecture

Contracts and decisions live in [`docs/adr/`](adr/); this document links to them rather than restating them.

## Activation

`src/extension.ts` calls `DBTPowerUserExtension.activate` in `src/dbtPowerUserExtension.ts`, the single activation path. Every collaborator is constructed beforehand by `compose` in `src/compositionRoot.ts`. Activation first checks for the conflicting upstream `innoverio.vscode-dbt-power-user` extension and blocks with one actionable error if present, then checks the resource-scoped `fusionPowerUser.enabled` setting. It then initializes the Project Registry, the Fusion client pool, and Fusion status reporting, registers Fusion client diagnostics, and builds the initial `Project` set. Startup is silent — only user-invoked actions and blocking configuration failures may show a notification (`src/fusion/fusionStatus.ts`).

## Declared Projects: Project Registry and Current Project

A Declared Project is a dbt project that receives independent editor services, scoped so a Dependency Project never gets its own service and nothing is discovered recursively, per [ADR 0003](adr/0003-scope-services-to-declared-projects.md). `ProjectRegistry` resolves the set per workspace folder from an explicit `fusionPowerUser.projects` list of relative or absolute roots, or the folder root itself when it contains `dbt_project.yml` and no list is set; any invalid entry or missing `dbt_project.yml` in an explicit list fails that folder's whole project set closed rather than silently dropping just the bad entry. `CurrentProject` resolves which Declared Project owns the file or command currently being handled, so nothing infers a project silently outside the active editor's project, a folder's sole project, a retained selection, or an explicit user pick.

## Executable resolution

`src/fusion/fusionExecutable.ts` resolves the `dbt` executable independently per Declared Project — the resource-scoped `fusionPowerUser.dbtPath` setting first, then `PATH` — never invoking or special-casing a tool manager; see the README for what that means for `mise-vscode` and similar shims. A resolution failure records a diagnostic for that project only and does not block sibling projects or activation. `--version` is checked against a minimum of 2.0.5; an untested newer major logs one terminal warning per major per installation, recorded in `globalState` and never a toast, then continues.

## dbt file associations

`package.json` contributes `filenamePatterns` for dbt's standard layout. For other layouts, "Configure dbt file associations" (`FileAssociationsCommand` in `src/features/projectSetup/fileAssociations.ts`) writes one `jinja-sql` glob per template path of every Declared Project, built by `dbtTemplateAssociations` in `src/dbt_integration/dbtAssociations.ts`. It writes user settings because VS Code rejects folder-scoped `files.associations`. Globs are absolute because a folder-relative `**/<dir>/**/*.sql` also matches dbt's compiled copies under `target/compiled/<project>/<dir>/`. VS Code globs have no escape character, so `*`, `?`, `[`, `]` and `}` are wrapped in one-character classes and `( ) !` stay literal; a literal `{` cannot be expressed because brace tracking also runs inside classes, so such directories are skipped, as is a template path equal to the project root, whose glob would capture `target/`. Each run removes `jinja-sql` template globs inside a project root that the project no longer declares, keeps every other entry, and compares keys case-insensitively on macOS and Windows, where VS Code matches globs case-insensitively. `src/test/vscodeGlob.ts` copies VS Code's glob matcher so tests check patterns against the real semantics.

## The Fusion client pool and operation routing

`src/fusion/fusionClientPool.ts` owns one `FusionClient` per Declared Project, created and torn down as the registry and launch-affecting configuration change, over a reverse socket (the client listens and passes `--socket <port>`), per [ADR 0002](adr/0002-use-the-native-fusion-lsp.md). The pool serializes reconciliation through an internal operation chain so overlapping registry and configuration events cannot race a client's replacement. Each client is launched from `toLspLaunch` over the project's snapshot; a settings change replaces the client only when that launch differs, and a manual or crash restart reuses the launch captured when the client was created, including the `FUSION_POWER_USER_LSP_COMPILED_OUTPUT` override read at that time.

Operation routing: the Fusion client is authoritative for realtime completions, hovers, definitions, references, renames, formatting, code actions, lenses, and diagnostics, and direct CLI invocations of the same resolved executable handle only operations the LSP has no command for. The legacy manifest-backed completion, definition and hover providers are deleted, and `vscode-languageclient` registers every provider Fusion advertises. Extension code lenses remain because Fusion returns none.

## Fusion client launch contract

`src/fusion/fusionLanguageClient.ts` and `src/core/lsp/` follow what the official dbt extension (`dbtLabsInc.dbt` 0.104.0 and 0.107.8, Fusion 2.0.5 and 2.0.6) was observed to do, plus fixes for Fusion behaviour it does not handle:

- **Compiled output.** `toLspLaunch` in `src/core/lsp/` always drops an inherited `DBT_LSP_USE_TARGET_LSP`. In the default `separate` mode (`fusionPowerUser.lsp.compiledOutput`) it sets the variable to `1`, as the official client always does, so the server compiles under `target/.lsp/` and `dbt.clearTarget` removes only that directory. In `shared` mode the variable is unset, so the server writes `target/compiled/` and `clearTarget` can delete all of `target/`, including the manifest the extension reads. `src/test/integration/targetIsolationRegression.test.ts` guards this. The spawn `cwd` is the project root.
- **Configuration.** `workspace/configuration` for section `dbt` answers only `{lsp:{linter:{enabled}}}`, so another extension's `dbt.*` settings cannot configure this server. The client never sends `dbt.compileLsp` or `dbt.clearTarget` on its own; the first `didOpen` compiles.
- **Command prefix.** `--command-prefix` is concatenated to command names with no separator, and the client registers the prefixed names the server advertises. Each project's prefix is `fusionPowerUser:<root digest>:`, so two clients (ours and the official one, or two Declared Projects) never register the same command id.
- **Command arguments.** `dbt.listNodes` takes `[selector]` (a dbt selector string); `dbt.getCurrentNode` takes `[relativePath]`, a bare project-relative path; `dbt.compileFile` takes `[uriString]`; `dbt.show` takes `[{uri, inline, limit}]`; `dbt.getProjectInfo` is sent with no `arguments`. The shapes tried before these returned `null`. The command inventory against Fusion 2.0.5 is in [`research/lsp-commands-fusion-2.0.5.md`](research/lsp-commands-fusion-2.0.5.md).
- **Document selector.** Each client's selector is a `RelativePattern` on its project root, which needs `vscode-languageclient` 10 (protocol 3.18); major 9 accepts only string patterns. The base is the root as a URI string, not a `vscode.Uri` or `WorkspaceFolder`, which can fail to convert. If a pattern fails to convert, the library leaves it `undefined`, which matches every document of that language, so `validateDocumentSelectorPatterns` throws instead. Overlapping Declared Project roots are not isolated.
- **Symlinked roots.** Fusion canonicalizes `--project-dir` but matches document URIs literally, so a project opened through a symlink loads nothing. `canonicalProjectRoot` launches on the realpath and installs `uriConverters` between the opened root and the realpath.
- **Diagnostics for missing files.** After each compile Fusion publishes about 134 empty diagnostics for files from its bundled adapter packages that do not exist under the project root. Under Cursor these left the renderer at 100% CPU. `ProjectDiagnosticsFilter` in `src/fusion/fusionDiagnostics.ts` drops a notification for a missing file unless it forwarded that URI before, so a deleted file still gets its clear.

## Output channels

`OutputChannels` (`src/projects/outputChannels.ts`) is the only module that calls `window.createOutputChannel`; the composition root builds one and passes it to everything that logs. Each Declared Project gets one `LogOutputChannel`, named `Fusion Power User: <project name>`. When the Project Registry holds another Declared Project with the same name at the time the channel is created, the name ends with the root digest, for example `Fusion Power User: general (k3J9…)`; a channel keeps its name for its lifetime. It is created on first use and keyed by the Declared Project object, so a registry change that replaces the Declared Project at a root also replaces its channel, and it is disposed when the Project Registry drops that Declared Project. The `OutputChannels` instance is itself the extension log, the `Fusion Power User` channel, which carries messages that belong to no Declared Project: registry reconciliation, pool failures, activation errors, and features that log before or without resolving a Project (the defer status bar, the lineage, query result and docs panels' webview traffic, the lineage service). Features that hold a Project when they log (project setup commands, the CTE profiler, the documentation and test services) write to that Project's channel through `Project.log` or `OutputChannels.logFor`. The diagnostics command writes its report to `Fusion Power User - Diagnostics`, which `OutputChannels` creates and `DiagnosticsOutputChannel` owns.

A Declared Project's channel carries everything about that project in one place, in time order:

- **Fusion Client.** The pool passes the channel to each client it starts as `outputChannel` and `traceOutputChannel`, so `vscode-languageclient` logs to it, takes its trace level from the channel's log level (Developer: Set Log Level), and does not dispose it. The server's stdout and stderr and the client's start, restart, and failure messages go to the same channel. A replacement client after a launch change reuses it, so the history before the restart stays visible.
- **dbt CLI.** `Project`, its `FusionCli`, `CommandProcessExecution`, and its manifest parsers log through the channel, including each command line and the streamed output of commands queued as tasks.

The extension no longer tails `logs/dbt.log`. Every dbt process the extension starts already streams its output to the channel, and the file also holds runs from terminals and other tools, so reading it duplicated lines and mixed in unrelated runs. Fusion's own file stays where Fusion writes it.

A channel wrapper drops writes after disposal, because VS Code throws on writes to a closed channel and an in-flight command or client teardown can still log after its project is removed. The language status item's "Show output" (`fusionPowerUser.showFusionOutput`) opens the client's channel, which is the project's channel. Error notifications from project setup commands name that channel.

In Cursor, showing a channel runs the Output view's own command for it, `workbench.action.output.show.<channel id>`, rather than `LogOutputChannel.show`. A log channel's id is the extension id, a dot and the channel name without the characters a file name cannot hold, followed by `.log` in VS Code and by `.workspaceId-<workspace id>` in Cursor. Cursor's `LogOutputChannel.show` looks the channel up by the id without that suffix, finds nothing, and leaves the Output view closed or on another channel. The wrapper detects Cursor from `env.uriScheme` or `env.appName`; VS Code keeps `LogOutputChannel.show`, which also reveals a hidden panel through the workbench's own handling. The wrapper caches the command id per channel and forgets it when the command fails.

When no command matches or it fails, the wrapper falls back to `LogOutputChannel.show`; this includes the first show in Cursor before the workbench has registered the channel's command.

## Artifacts, caches and persisted state

The extension reads a Fusion artifact only after a command it launched and awaited, or where the protocol cannot supply the data; it never republishes project state on a write under `target/`, and never writes into it. `ManifestTrigger`'s source globs also match files under `target/` and filter them by path. It does not persist derived compiler state or query results, and keeps no second diagnostic store beside the language client's collections. Query rows live in memory until their tab closes. Submitted SQL for a given logical query stays byte-identical, because Snowflake's result cache requires an exact text match; a comment carrying a timestamp or run id would defeat it.

## The metadata port

The codebase is manifest-driven: `dbt parse` produces `manifest.json`, and `Project` (`src/projects/project.ts`) builds the metadata maps through `ManifestRebuild` behind `ManifestCacheProjectAddedEvent` (`src/dbt_client/event/manifestCacheChangedEvent.ts`). `src/metadata/projectMetadataSource.ts` declares `ProjectMetadataSource`, the port every producer implements; `src/metadata/manifestMetadataSource.ts` is the only implementation, a thin adapter over `Project.rebuildManifest` and manifest publication. Every panel, tree, lens, and language provider consumes the event through `QueryManifestService`, which is the sole mediator and must not gain a second consumer seam.

The Fusion LSP does not populate this port: `dbt.getProjectInfo`, `dbt.listNodes`, and `dbt.getCurrentNode` lack macros, docs, exposures, tests, metrics, semantic models, and depth inputs (see [`docs/lsp-metadata-gaps.md`](lsp-metadata-gaps.md)). A source that always refuses to publish is dead code, so no LSP metadata source exists; the manifest source remains selected until a contract-complete LSP payload exists.

`Project` runs dbt through `FusionCli`, owns model, macro, seed, and `dbt_project.yml` watching, and reads `run_results.json` only after a command it launched and awaited, comparing pre- and post-command content; it has no ambient `target/` watcher.

## Panels and webview messaging

Three panels remain: query results, the local documentation editor, and lineage (`src/features/queryResults/`, `src/features/docs/`, `src/features/lineage/`). Each registers as a `WebviewViewProvider` with `retainContextWhenHidden`. `QueryResultPanel` and `LineagePanel` extend `PanelHost` (`src/webview/panelHost.ts`), which renders the panel's entry and routes common commands; `LineageViewProvider` is the registered sidebar host that delegates to `LineagePanel`. The extension host and the webview (React 18 + Vite + Redux Toolkit, built separately under `webview_panels/`) communicate through `postMessage`/`onDidReceiveMessage` with typed message contracts.

Every panel page comes from `panelHtml` (`src/webview/panelHtml.ts`), the only HTML and Content Security Policy generator. Each panel has one Vite entry in `webview_panels/src/entries/`; `panelHtml` reads the build's `manifest.json` and loads only that entry's script and stylesheets. The policy starts from `default-src 'none'` and each panel declares the allowances its entry needs as a `PanelCsp`. [`webview-csp-october-2026.md`](research/webview-csp-october-2026.md) records the evidence for each directive, including `'wasm-unsafe-eval'` in place of `'unsafe-eval'` for Perspective.

The message types live in `packages/webview-contract/` (`@fusion-power-user/webview-contract`), an npm workspace that both bundles import from its built `dist`; rsbuild and Vite bundle it, so it never ships under `packages/`. The repository has one `package-lock.json`, at the root, covering the contract and `webview_panels`. Every public build, watch and dev entrypoint first builds the contract, and composite entrypoints call the internal `:app` scripts so one command starts at most one contract watcher. Vitest aliases the package name to its `src/index.ts`, so contract tests run without a build. Its `tsconfig.json` loads neither `vscode` nor DOM types, because both the extension host and the webview import it.

Each panel module exports `HostMessage` and `PanelMessage` unions and `isHostMessage`/`isPanelMessage` guards. A guard is built from one field-check map per command, typed by `CommandFields`, so a field added to a union without a check, or a check for an undeclared field, is a compile error. Every host panel routes inbound messages through `dispatchMessage` (`src/webview/messageRouter.ts`): the panel's guard, then a `Handlers` map keyed on `command` that the compiler requires to be exhaustive. A rejected message is logged as a warning to the extension log and dropped; a handler that throws is logged as an error. Outbound `postMessage` calls take the panel's `HostMessage`. Lineage persists its edge-visibility and relationship-overlay settings in global state; `defaultExpansion` stays a user setting.
